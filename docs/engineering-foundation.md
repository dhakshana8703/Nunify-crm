# Engineering foundation specification

Goutham's Dev Stories are the product reference. Local copies are in `docs/stories/`. The original plan starts with Cvent and introduces Directory of Associations in R4. Dhakshana's engineering brief brings **Cvent and Directory of Associations into the shared CRM from the start**. Use each story's acceptance criteria across both sources wherever the rule concerns shared accounts, contacts, suppression or sales history.

Use the existing Flask app, relational store, and worker with hexagonal boundaries. Cvent and Directory saved exports attach as separate adapters. A compatible external scraper attaches through the ingest API. Source parsing stays at the connector boundary, and the core owns admission, account identity, suppression, and sales workflow decisions. A new native format or source-specific business policy needs its own implementation and tests.

## Boundaries and rollout

The core owns write decisions and business rules. It imports neither Flask, a database driver, nor a scraper implementation. Adapters use the core contract and contain storage, transport or source-format details. The web app and worker select adapters at startup. Existing saved source IDs, review state and API contracts remain durable.

Write the acceptance cases before implementation. Capture a failing regression or boundary check, make the smallest change that passes, and run existing workflow tests. For refactors, keep passing behavior checks as a baseline. Correct fixture errors while retaining the written assertion. Record the exact tests and evidence in `working.md`.

R1-01 account-level stored flags and standardized reason and source metadata are product acceptance work. A full legacy identity merge, production restore proof, and the real-provider and hosting checks need their designated data, settings or approvals. Exercise them only in the appropriate environment. Preserve current database rows and use offline providers throughout this foundation change.

## Whole-application boundary checks

Each rule that controls a CRM decision must have an entry point that can be called with plain data and fake ports. A Flask adapter owns HTTP, session handling, signed requests, input decoding, and rendering. A persistence adapter owns SQL and transaction mechanics. A connector owns source or provider protocols and formatting. The core owns permissions based on CRM roles and relationships, state transitions, validation of business rules, and decisions to read, save or send through its ports. The web app and worker assemble those dependencies. SQL-backed read models may build reports and page projections using the existing storage schema. Presentation formatting stays at the edge.

The boundary change preserves existing product behavior, schemas where practical, user roles and saved records. The test suite checks every core module's dependencies and rejects direct SQL in Flask endpoints. Record any remaining entry point that still combines a core decision with an implementation, including the exact decision and why it remains. Completion requires evidence for each boundary rather than a file move or an import check alone.
